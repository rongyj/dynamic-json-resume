Based on my experience at McKinsey migrating mainframe EDA systems to AWS, here's my most challenging debugging story:
While refactoring a complex IBM MQ-based mainframe system to AWS using EventBridge, Lambda, and EKS, we encountered a critical issue where XML messages from the legacy mainframe were being silently dropped after processing through our SpringBoot EKS router. The system was designed to convert XML/XSD messages to JSON schema and integrate with EventBridge, but approximately 15% of messages were failing without any error logs. The infrastructure appeared healthy - EKS pods were running, EventBridge was receiving events, and CloudWatch showed successful Lambda invocations.
After implementing comprehensive monitoring using our custom CloudWatch metrics module across Lambda, EventBridge, and DynamoDB, I discovered the issue was in the SpringBoot application's XML-to-JSON conversion logic. The application code was using a strict XSD validation that didn't account for namespace variations in legacy mainframe-generated XML. What made this non-obvious was that the SpringBoot router logged these as successful conversions because it had a catch-all exception handler that defaulted to an empty JSON schema when parsing failed. The infrastructure happily processed these empty events downstream, making it appear as though everything was working correctly.
The solution required refactoring the SpringBoot application to handle dynamic namespace resolution and implementing a multi-stage validation pipeline. I also modified our EventBridge rules to include message validation before processing and created dead-letter queues in SQS for failed conversions. Additionally, I enhanced our CloudWatch monitoring module to track schema conversion failures as custom metrics. This experience highlighted how legacy system migrations require deep understanding of both the application's data transformation logic and the cloud infrastructure's event processing behavior - neither could be debugged in isolation.
